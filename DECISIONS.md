# SpeakCoach — Architecture & Technical Decisions

## 1. Core Stack & Build Tooling
- **Runtime & Packaging**: Capacitor 6 packages the app as a standalone Android APK. There is no application-owned backend; users configure their own AI providers and API keys.
- **Web UI**: TypeScript, vanilla DOM components, and Vite.
- **Testing**: Vitest covers provider routing, request handling, IELTS session logic, storage, audio helpers, and UI behavior. CI runs unit tests and builds the Android APK.

## 2. Networking & API Security
- **Native HTTP**: Capacitor's `CapacitorHttp` is wrapped by `httpClient.ts`. Provider base URLs and endpoint overrides remain configurable so compatible gateways and VPN-routed connections can be used.
- **Authentication**: Official Google Gemini requests use the `x-goog-api-key` header. Custom gateways continue to use the configured authentication style (Bearer, custom header, or query parameter) when required by that gateway. API keys must not be added to ordinary request URLs by default.
- **Timeouts and retries**: Timeouts are bounded and reported clearly. Billable AI `POST` requests are not automatically replayed after ambiguous timeouts, network failures, or server errors because the provider may already have processed the request. An explicit HTTP 429 rate-limit response may be retried within the configured limit. Users can manually retry failed evaluations or generation requests.
- **Diagnostics**: Request URLs and error details must redact credentials. Diagnostic logs must never contain raw API keys.

## 3. On-Device Key & Data Storage
- **Android minimum version**: Android 6.0 (API 23). Android 5.1 (API 22) and older are not supported. The minimum SDK is set in `android/variables.gradle` and must remain aligned with the Android Keystore implementation.
- **Key encryption**: Android API keys use AES-256-GCM through Android Keystore. The API-22 RSA-wrapped AES compatibility fallback is not part of the supported implementation.
- Android API keys are stored through `keyStore.ts` and the native `SecureKey` plugin, using Android Keystore-backed encryption. A successful write is verified before any legacy copy is removed.
- Legacy Preferences/localStorage keys may be read and migrated. If migration fails, the old copy is retained to avoid data loss.
- Browser-only development may use browser storage; it is not equivalent to Android Keystore protection.
- AI settings backups may contain readable API keys and must be treated as secrets. Test-data backups must not contain API keys.
- Existing storage keys and plugin identifiers are retained for compatibility. Renaming them requires an explicit migration and backup-restore tests.

## 4. Speech, Recording & TTS
- **Recording**: The Android `SpeakCoachSpeechPlugin` is implemented in Java. Online audio capture records 16 kHz mono PCM WAV for supported STT endpoints. Desktop development uses a Web Audio fallback.
- **System speech recognition**: Shadowing and IELTS may use Android `SpeechRecognizer` as a local/system fallback. Android's `EXTRA_PREFER_OFFLINE` is only a preference; a device's recognition service may still use a network service. On-device recognition is used when Android exposes it and the device supports it. SpeakCoach does not bundle its own speech model.
- **Long answers**: Android system recognition behavior varies by device and may stop after silence. Long IELTS Part 2 answers require real-device testing; the app must clearly report recognition errors and must not pretend recording started when the recognizer could not start.
- **TTS**: Online neural TTS is preferred when a configured provider is available. Android native TTS remains an allowed offline fallback and must be labelled as offline/basic so users understand that an online neural voice may sound better.
- **Backgrounding**: Moving the app to the background stops TTS and active microphone capture. An active IELTS attempt is paused safely; completed answers and the current step are retained, while an interrupted answer must be recorded again after returning.

## 5. IELTS Question Generation & Assessment
- **Question generation**: The production app does not ship a prewritten IELTS question bank. New question sets and replacement questions are generated by AI. Previously generated sets may be saved locally and reused later; they are not a built-in question bank.
- **Speech-to-text**: IELTS may use a configured online STT provider or Android system recognition. Offline/system recognition remains an allowed fallback.
- **AI evaluation**: Online API evaluation is the preferred path. If no verified evaluator is available, SpeakCoach does not generate offline IELTS evaluations. If an online evaluation fails, the answers and transcript remain in History for a later retry.
- **Re-evaluation**: Saved answers can be evaluated again when connectivity returns or when another provider is configured. API 1 and API 2 are explicit choices. Each successful evaluation is retained in evaluation history so a new run does not erase earlier results.
- **Assessment validity**: AI-generated bands are learning estimates, not official IELTS results. Speech-recognition confidence is not a pronunciation score. Until a validated pronunciation-assessment provider is active, IELTS Pronunciation remains “Not assessed” and is excluded from the practice estimate.
- **Short or missing answers**: No band estimate is produced when there is insufficient speech evidence.

## 6. Session & UI Reliability
- Network connectivity changes update connectivity state and diagnostics without rebuilding an active view. A stale asynchronous refresh must not overwrite a newer route.
- Background/foreground transitions must release microphone and TTS resources. Interrupted answers are not silently submitted as complete answers.
- UI controls must remain usable on narrow phone screens, with adequate touch targets in both light and dark themes.
- The app interface supports English and Persian (فارسی). Shadowing practice supports the languages available in its language catalogue; IELTS prompts and examiner feedback remain in English.

## 7. Backup & Restore Compatibility
- AI settings restore validates the full import, snapshots the previous configuration, verifies key/config writes, and attempts rollback if any stage fails.
- Test-data backup includes IELTS history, saved AI-generated question sets, and drafts. Evaluation history is optional in older backups; absence of the new field must not invalidate or erase older records.
- Changes to storage schemas must be additive and backward-compatible where possible. Do not rename existing API-key storage identifiers without a tested migration.

## 8. Android Release & Distribution
- The Android application ID is `com.ariyand.speakcoach`. The initial public release was `1.0.0` (`versionCode` 1); the current published release is `1.1.4` (`versionCode` 19).
- A stable Release APK requires a persistent signing keystore. The current development workflow may build Debug and unsigned Release artifacts until the user chooses to configure release signing.
- Keep the same package ID and signing certificate for every future update. GitHub Releases are the update source; the in-app updater compares semantic versions and only offers signed APK assets attached to published full releases.
- Capacitor/Target SDK upgrades are scheduled for the point when distribution requirements make them necessary; they should be done in an isolated branch with device verification.


## 9. Shadowing Generation Variety (2026-11-27)
- Keep the Persian RTL Grammar language-toggle positioning fix from `fix/persian-grammar-language-toggle-position`; it is included in `feat/shadowing-variety` and is unrelated to the generator changes.
- Generate `N+2` candidates in the first request, validate locally, and use one repair request for the missing count. The generation path is capped at **two HTTP requests total**: API 1 first, then API 2 when verified/available; a repair uses the other available account where possible. Transport-level automatic retries are disabled for these generation requests so they cannot silently exceed the budget.
- Keep the exact 20-sentence AI-set contract. Single-sentence generation uses the same slot/validation path but returns one item.
- Persist shuffled situation, speech-act, grammar, focus, and prompt-variant decks by language and level. Keep a 120-entry ring buffer of compact sentence memory per language and level. Old `speakcoach_shadowing_recent_sentences_v1` and `v2.<lang>` values are migration inputs, and history sets seed the new memory.
- Use character 3-gram and token Jaccard similarity, language-aware opening keys, and local word-count/focus checks. No extra model calls are used for variety or validation.
- Language defaults: Portuguese remains `pt-PT`; Arabic uses readable MSA; phonetic-focus text remains in the target language. Orthography follows the target language's STT-friendly form (including no Arabic harakat, no pinyin/furigana, Persian ZWNJ, and standard Korean spacing). A future optional flag could allow phonetic-focus language to follow the UI language; it is not enabled in this change.
- Prompt-size estimate for a representative English/Easy 22-slot batch: old prompt **3,874 characters / about 969 tokens**; compact prompt **1,848 characters / about 462 tokens** using the agreed chars/4 estimate. A randomized 15-language × 4-level slot simulation with a full eight-opening/eight-keyword avoid line peaked at about **583 tokens** (or about 597 with the maximum 48-character topic constraint) with the full eight-opening/eight-keyword avoid line. Actual provider tokenizers can differ. The representative prompt is about 52% shorter by this estimate.
- Root causes a–e from the implementation brief were confirmed in the previous generator: static prompt/no per-sentence assignment; six-sentence shared-per-language memory; exact-only duplicate detection; English-oriented examples; and no per-item structure for a 20-item batch.
- The model-answer redesign for IELTS remains out of scope; IELTS uses the same slots, level-specific memory, and local validation only.
